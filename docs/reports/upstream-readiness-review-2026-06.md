## 総評

**バックエンド本体（`llvm/lib/Target/S1C33/`）の設計品質は Lanai / CSKY 級で upstream に
出せる水準**。ただし現状のまま PR を出すと**確実にリジェクトされる箇所が 3 つ**
（compiler-rt のライセンス問題、BareMetal ドライバのベンダ固有リンクライン、
lit.local.cfg 欠落）、**ほぼ確実に修正要求が来る箇所が多数**（clang-format 違反 923 件、
テスト不足、日本語コメント等）ある。

## 🔴 ブロッカー（このままでは絶対に通らない）

### 1. compiler-rt builtins — ライセンス上 upstream 不可能

`compiler-rt/lib/builtins/s1c33/*.S` 全 19 ファイルの先頭に:

```
; Recovered from fp.a — adddf3.o
; Auto-generated by objdump2asm.py, do not edit
```

EPSON のプロプライエタリライブラリ（fp.lib / idiv.lib）を逆アセンブルした派生物である
ことをファイル自身が明記しており、Apache-2.0-with-LLVM-exception での再ライセンスは
EPSON の許諾なしには法的に不可能。LLVM ライセンスヘッダも EPSON 著作権表示もない。
**upstream PR からはこのディレクトリ全体を除外する必要がある**（バックエンド本体とは
独立なので除外自体は容易。upstream 版では generic C 実装の builtins がそのまま使える）。
なお CMake 配線（`builtins/CMakeLists.txt:766-818` 周辺、`builtin-config-ix.cmake` 等）
自体は他ターゲットの流儀に沿った良い出来。

### 2. BareMetal.cpp のベンダ固有リンクライン

`clang/lib/Driver/ToolChains/BareMetal.cpp:720` 以降で `-lpceapi` / `-lpceshim` /
`-lcxxrt` / `--start-group` という P/ECE 固有のリンク順序をジェネリックな BareMetal
ツールチェーンにハードコードしている。コメントにも「newlib Phase 2 Stage B」など
プロジェクト内部の事情が書かれている。upstream のドライバメンテナはベンダ SDK の
ライブラリ名を共通コードに置くことを認めない。upstream 版では
`-lclang_rt.builtins-s1c33 -lc -lm` 程度に削るか、専用 ToolChain サブクラスに分離する
必要がある。

一方、`-fno-exceptions` / `-fno-rtti` のターゲット既定値（`ToolChain.cpp` /
`Clang.cpp`）は xcore / PS4 と同じパターンなので、理由コメントがあれば通る見込み。

### 3. `lit.local.cfg` の欠落

`llvm/test/CodeGen/S1C33/` と `llvm/test/MC/S1C33/` のどちらにも `lit.local.cfg` がない。
experimental target は既定ではビルドされないため、**S1C33 を有効化していない全ビルド
ボットで 40 本のテストが即 fail する**。Lanai 等と同様に以下が必須:

```python
if not "S1C33" in config.root.targets:
    config.unsupported = True
```

PR を出した瞬間に precommit CI が赤くなるレベルの問題。

### 6. lldb の汎用バグ修正が S1C33 変更に混在

`lldb/source/Plugins/Disassembler/LLVMC/DisassemblerLLVMC.cpp` の修正

### 7. テストカバレッジの穴

テスト量自体は良好（CodeGen 34 本 + MC 6 本、ハンドライン CHECK も ABI コメント付きで
質が高い。テスト/コード比 ≈ 35%）だが、新規ターゲット PR で必ず要求される領域が空白:

| 欠落領域 | 内容 |
|---|---|
| clang Driver テスト | リンクライン、`-fno-exceptions`/`-fno-rtti` 既定、デフォルトリンカ — **0 本** |
| clang Sema テスト | `interrupt_handler` 属性の誤用検出（非関数への付与等）— **0 本** |
| MC ネガティブテスト | 不正命令・範囲外即値・不正オペランドの `// CHECK: error:` — **0 本** |
| i64 演算 | libcall 展開経路の直接テストなし |
| AsmParser エラー診断 | 同上 |

clang 側テストは `clang/test/CodeGen/S1C33/single-element-struct.c` の 1 本のみ。内容
自体は優秀（8 関数で単一要素 struct ABI のエッジケースを網羅）だが、ターゲット追加 PR
としては薄すぎると指摘される。

### 8. lld CMakeLists のアルファベット順違反

`lld/ELF/CMakeLists.txt:32` — `Arch/S1C33.cpp` が MSP430 と PPC の間に挿入されている。
正しくは RISCV と SPARCV9 の間。典型的な nit だが必ず拾われる。

### 9. ELF relocation 番号と psABI 不在

`EM_SE_C33 = 107` は**正式割当済みの EM 値**なので問題なし（これは強み）。一方
relocation 番号には公式の割当が見つからない: ELF を採用している S5U1C33001C（xgcc）
ツールチェインの relocation 番号資料は発見できず、gcc33（S5U1C33000C）はそもそも
SRF フォーマットなので ELF relocation 番号自体が存在しない。そのため本ポートが自前で
値を割り当てている（セマンティクスは gcc33 SRF の relocation 種別を 1:1 で踏襲し、
srf2elf がこの番号にマップする）。`S1C33ELFObjectWriter.cpp` / `ELFRelocs/S1C33.def` に
この出典と安定性を説明するコメントが必要で、レビューで必ず質問される。
`R_S1C33_REL_AH/AL` のような独自追加 relocation は特に。

## 🟡 レビューで質問されそうな点（説明があれば通る）

精査結果（2026-06-10）を含めて更新。①④で当初認識より深い問題、②で潜在ハザードを発見。

- **① `S1C33ISelLowering.cpp` の dead ガード** — `combineAndSraBias` の
  `if (4 + AndCost <= 4)` は常に偽。精査の結果、**sibling の `combineSrlSraBias` の
  `if (ShiftCost <= 4)` も常に偽**（`4 + ceil(K/8) ≥ 5`）。どちらも「sra 31 だけで
  4 命令なので置換は常に得」という正しい推論が死んだ比較として書かれていた。
  → **対応済み**: 両ガードを削除し推論をコメント化（挙動不変）。
- **② `EXT` の `hasSideEffects = 1`** — 当初の「0 にすべきでは」という見立ては**誤り**。
  EXT は `eliminateFrameIndex`（PEI = post-RA スケジューラ前）でも生成されるため、
  このフラグが barrier chain（`isGlobalMemoryObject`）として後続メモリ命令の繰り上げを
  防いでいる。→ **②a 対応済み**: 根拠コメントを追加。
  **②b → 対応済み**（コミット `2bce1ad7`、実機確認済み 2026-06-10）: barrier は
  純 ALU 命令の挟み込みや EXT 後の独立 2 ロードの入れ替えまでは禁止できず、構造上の
  潜在ハザードが残っていた（再現試行では list scheduler のソース順タイブレークにより
  分離せず、発現実績なし）。恒久対策として `*_sp_off` pseudo 8 個を新設し、
  eliminateFrameIndex は opcode 差し替えのみ、EXT 生成は ExpandExtPseudos
  （スケジューラ後）に統一した。これで裸の ext+対象ペアが PEI〜post-RA スケジューラ間に
  存在する窓が消滅。lit 全 42 パス、pmdplay.elf / hello.elf はバイナリ完全一致。
  副次的発見: emitPrologue の `WordSize <= 1023` assert によりフレームは最大
  4092 バイト（`sub %sp, imm10` 1 段のみ）で、SP オフセット用 2-ext 分岐は元々
  到達不能なデッドコードだった（新ヘルパにも防御的に残置）。4KB 超フレームは
  別件の未実装事項。
- **③ relaxation 戦略**（EXT0→EXT2 直行）— `S1C33AsmBackend.cpp` にコメント済み。
  PR 説明文マターでありフォークでは**対応不要**。
- **④ `MOV_ri19`** — 当初指摘（`Defs = [PSR]` のコメント不足）より重要な問題を発見:
  コメントが「`isAsCheapAsAMove` is NOT set」と書いているのにコードは
  `isAsCheapAsAMove = 1`。コミット `a0030fc` が旧ドラフトのコメントとフラグ設定を
  同時に入れたもので、コミットメッセージの損益分析（spill 3+N vs remat 2N）から
  **コードが正、コメントが stale**。→ **対応済み**: コミットメッセージの分析を
  コメントに移植し、`Defs = [PSR]` の参照（MOV_ri32 の説明へ）も追加。
- **⑤ `S1C33MCCodeEmitter.cpp` の `0x6C00`** → **対応済み**: Class 3
  `ld.w %rd, sign6` 基底オペコードである旨をコメント追加。
- **⑥ `S1C33AsmBackend.cpp` の `fixup_s1c33_abs_l` offset=4** — `MCFixupKindInfo` の
  `TargetOffset` は**ビット単位**（sign6 = bits[9:4] → offset 4, width 6）で整合して
  いた（当初レビューはバイトと誤読）。→ **対応済み**: ビット単位である旨をコメント追加。

### 項目 2 補足: P/ECE toolchain サブクラス化の設計メモ

BareMetal から P/ECE 専用 ToolChain サブクラスを分離する場合、**バックエンド名
（S1C33）は変えない**。コード生成は triple の arch フィールドしか見ないため影響なし。
判別子の置き場所は 3 案:

1. **OS フィールドに `piece` を追加**（`s1c33-none-piece`）— P/ECE は「固定アドレスに
   カーネル API を持つプラットフォーム」なので意味的に最適。PS4 の `x86_64-scei-ps4` が
   近い前例。`Triple.h` の `OSType` + パーサに数行追加し、`Driver.cpp` の getToolChain で
   `PIECEToolChain` にディスパッチ。`__PIECE__` マクロ等も OS 判定で出せる。
   generic な `s1c33-none-elf` は素の BareMetal に落ち、`s1c33-none-piece` だけが
   P/ECE リンクラインを持つ、という分離になり upstream 的に最も綺麗。
2. **vendor フィールドに `piece`**（`s1c33-piece-elf`）— 動くが「P/ECE はベンダか？」
   という違和感あり。
3. **triple 変更なし、arch だけで専用 ToolChain クラス**（AVR / MSP430 方式）— 一番軽い。
   「s1c33 ユーザー ≈ P/ECE ユーザー」が成り立つ間は十分で、既存のビルドスクリプトも
   無修正で済む。フォーク運用の実利だけならこれを推奨。

### 項目 7 の対応（2026-06-11）: テストカバレッジの穴を解消

レビューで空白とされた 4 領域すべてにテストを追加した（llvm サブモジュール 5 コミット +
親リポジトリの Makefile 拡張）。テスト作成の過程で**実バグ 3 件**を発見・修正した:

1. **`ext` 即値のサイレント切り詰め**（コミット `669ff6fe`）— EXT のオペランドが
   素の `i32imm` で範囲チェックがなく、`ext 9000` が `ext 808` にアセンブルされていた。
   `def EXT` で uimm13 にオーバーライド（`ext sym@ah` 等のシンボリックは従来どおり
   fixup 委譲）。これによりデッドコードだった `Match_InvalidUImm13` 診断も到達可能化。
2. **定数 PC 相対変位のサイレント切り詰め**（同コミット）— simm8 に ParserMatchClass が
   なく、`jreq 300` が sign8=44 として黙ってエンコードされていた（定数は
   fixup/relaxation 経路を通らず encoder がマスクするだけ）。SImm8 オペランドクラスを
   追加し定数のみ [-128, 127] を強制（ラベルは従来どおり）。
3. **ELFObjectWriter の segfault**（コミット `31a8980c`、**generic MC バグ**）—
   ローカルな絶対シンボル（`bigsym = 0x4000000`）+ 関係指定子（`ext bigsym@ah`）で
   セクションシンボル変換が null セクションを参照してクラッシュ。`SecA` ガードを追加し
   SHN_ABS シンボルをそのまま relocation に保持。lldb の CommentStream 修正と同様、
   単体で upstream に出せる generic 修正。
