# ディレイスロット充填パスの候補命令規定

`S1C33DelaySlotFiller.cpp`（`llvm/llvm/lib/Target/S1C33/`）が、ディレイド分岐の
直後1命令（ディレイスロット）に既存命令を移動して充填するパス。本書はその
**候補命令の選定規定**と、**マニュアル規定との差**をまとめる。

関連: DESIGN_SPEC.md §4.3、`docs/errata.md`、CPUマニュアル pp.30 §2.5.12。

## マニュアル規定・実機実態・本バックエンドの立ち位置

ディレイスロットに置ける命令については、3つの「層」がある。本バックエンドは
その**中間**に保守的な線を引いている。

### 1. マニュアルの規定（最も厳格）

S1C33000 コアCPUマニュアル pp.30 §2.5.12「分岐命令・ディレイド命令」では、
ディレイスロットに置ける命令を**ホワイトリスト（列挙）で規定**しており、
そこに挙がっていない命令はスロットに置くことを**禁止**している。

### 2. 実機の実態（最も寛容）

実機検証の結果、マニュアルのホワイトリストに挙がっていない命令——
**`mlt.w` のような多サイクル命令、`ld.w %rd, [%rs]` のようなメモリアクセス命令、
さらには `ext` 拡張命令まで**——ディレイスロットに入れても正しく動作することが
分かっている。実機はマニュアルの列挙より大幅に寛容である。

### 3. 本バックエンドの立ち位置（中間の保守ライン）

実機がそこまで寛容だと分かっていても、本バックエンドは**そこまでは踏み込まない**。
次の**原則**を満たす命令までを許可し、それ以上は活用しない立場を採る。

> **「1サイクル命令・メモリアクセス不可・ext拡張不可・分岐不可」**

すなわち、マニュアルのホワイトリストよりは広く（ホワイトリスト外でも原則を
満たせば許可する）、実機の実態よりは狭く（多サイクル命令・メモリアクセス・ext は
実機で動くと分かっていても許可しない）線を引く。

判定方式は、ホワイトリストへの一致ではなく上記の原則を満たすかを見る
**ブラックリスト方式**——「既知のNG条件に該当しなければ適格」とする。

> **重要：この方針の帰結として、マニュアル pp.30 §2.5.12 のホワイトリストに
> 明示されていない命令でも、上記の原則（下記の拒否条件）に該当しない限り
> ディレイスロットに選ばれる。** これはマニュアル規定からの意図的な逸脱であり、
> 実機の寛容さの観察に基づく設計判断である。同時に、実機ではさらに寛容に
> 動くと分かっている `mlt.w` / メモリアクセス / `ext` は、保守的判断により
> **あえて許可していない**。

ブラックリスト方式を採る理由は、原則ベースで判定するほうが、マニュアルの
ホワイトリストを命令追加のたびに追従させるよりも、新規命令に対して保守的かつ
網羅的に効くため。その代わり、いくつかの前提に依存する点に留意すること（後述）。

## 対象とする分岐

スロット充填の対象は次の3命令のみ。

| 変換元 | 変換先 |
|---|---|
| `JP_i`   | `JP_D_i`   |
| `RET`    | `RET_D`    |
| `CALL_r` | `CALL_r_D` |

`jp.d %rb`（レジスタ間接ディレイド分岐）はハードウェアバグのため生成禁止であり、
変換対象に**含めていない**（DESIGN_SPEC.md §4.3、errata §1）。

充填できる候補が見つからなければ非ディレイド命令のまま据え置く（`nop` は挿入せず、
分岐命令そのものを非ディレイド形のまま残す）。

## 候補選定の3段フィルタ

`findDelaySlotCandidate()` が分岐から後方へ命令を走査し、次の3条件をすべて満たす
最初の命令を採用する。

### 1. 命令単体の適格性 — `isDelaySlotCandidate()`

以下のいずれかに該当する命令は**不適格**。これらが「1サイクル・メモリ不可・
ext不可・分岐不可」の原則をブラックリストとして具体化したものである。

| 拒否条件 | 対応する原則／根拠 |
|---|---|
| 疑似命令（`isPseudo()`） | 実体を持たない |
| `EXT` 命令 | ext拡張不可。次命令を直接修飾するため分離不可 |
| 終端・分岐・呼び出し・復帰命令 | 分岐不可 |
| メモリアクセス命令（`mayLoad()` / `mayStore()`） | メモリアクセス不可 |
| 未モデル化の副作用を持つ命令（`hasUnmodeledSideEffects()`） | 安全側に倒す |
| `MLT_W` / `MLTU_W` / `MAC` | 1サイクル制約。多サイクル命令（mlt.w/mltu.w=5cyc、mac=2n+4cyc） |
| SP を定義する命令（`add/sub %sp` 等） | `ret.d` は遅延スロット実行後に `[SP]` から戻り番地を読む。スロットで SP を変えると誤位置を読む（`popn` 問題と同根） |
| 2バイトを超える命令（`getDesc().getSize() > 2`） | ext拡張不可。ext 付き命令の検出 |

### 2. 分岐先レジスタとの競合 — `hasBranchHazard()`

`CALL_r` / `CALL_r_D` では、候補命令が分岐先レジスタを定義していないことを確認する。
スロットでターゲットレジスタを書き換えると呼び出し先が変わってしまう。

### 3. 介在命令とのレジスタ依存 — `hasRegisterHazard()`

候補命令と、それ以降（分岐との間）に挟まる「介在命令」との間に
def-use / def-def ハザードがないことを確認する。さらに、候補命令の直前が `EXT` の
場合（その候補は ext に修飾される側）はその候補を使えない。

`PUSHN` / `POPN` のレンジ動作と暗黙の SP 操作は `definesRegisterSemantically()` /
`readsRegisterSemantically()` が明示展開し、`MI.definesRegister()` 単独では
捕まらないレジスタ作用も拾う。

## ブラックリスト方式が依存する前提

マニュアルのホワイトリストを超えて許可する以上、本パスは次の前提が崩れると
原則に反する命令をスロットに充填しうる。新規命令を追加する際は必ず確認すること。

- **1サイクル制約**は、多サイクル命令を個別に列挙して弾くこと（現状 `MLT_W` /
  `MLTU_W` / `MAC`）でしか担保していない。将来、新たな多サイクル命令を
  TableGen に追加した場合、`isDelaySlotCandidate()` の明示拒否リストにも
  追加しなければ、誤ってスロットに充填されうる。
- **副作用**は `hasUnmodeledSideEffects()` と `mayLoad` / `mayStore` でしか
  捕捉していない。TableGen 側の `hasSideEffects` / `mayLoad` / `mayStore` /
  `Defs` 指定が正しいことが前提となる。

新規命令を追加する際は、それがディレイスロットに入って安全か（1サイクルで完結し、
メモリにも分岐にも副作用にも触れないか）を確認し、危険なら
`isDelaySlotCandidate()` の拒否リストへ追加すること。なお、実機では `mlt.w` /
メモリアクセス / `ext` も動くと分かっているが、本パスは保守的方針によりこれらを
許可しない——この線を緩める場合は実機検証を伴う明示的な設計判断として行うこと。
